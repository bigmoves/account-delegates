Account delegates

One fact on the account. Three ways to use it. A community, a brand, a newsroom: one DID, several people who legitimately write to it, and no shared secret anywhere.

Today

A shared password, or app passwords passed around a group chat. Every write looks the same. Nobody can be removed without rotating the secret. Nothing records who did what.

Here

The account names its delegates and what each may do. A delegate acts as themselves, bounded by the account, attributed after the fact, revocable at once. Nobody ever holds the account's credential.

1 · Delegated write

The person's own app, their own session. A service auth token from their PDS, repo set to the account. One login, no client needs to know the account exists.

2 · Sign in as the account

Any OAuth client, unchanged. The account's PDS authenticates the person at their PDS, checks the config, and issues the account's session, narrowed, with act.sub.

3 · Create from an app

The founder's app creates the community's account on any PDS with the founder's own service auth. No usable credentials; the founder is a controller. The app holds nothing.

Same bounds, same matcher the PDS already uses for OAuth scopes, same per-write log for all three.

What a delegated session gets

The client asked for

atproto repo:social.grain.group.item repo:app.bsky.feed.post?action=create blob:image/*

The account allows alice

repo:social.grain.group.item?action=create&action=delete

The token alice gets, as the account

atproto repo:social.grain.group.item?action=create&action=delete repo:app.bsky.feed.post?action=create blob:image/* act: { sub: did:plc:alice }

The intersection, applied at issue and again on every request against the account's current configuration. Remove alice and the session is refused on its next use and cannot be refreshed.

A controller additionally keeps account:delegates?action=manage, so the account's settings tool works for them. Nobody else's session keeps any account:, identity:, or rpc: scope.

7

Attribution, revocation, policy

Attribution

Every delegated write is logged on the account's PDS: delegate, URI, method, time, and which path it took. A delegated session carries act.sub in its token and in getSession. The commit itself is the account's: nothing on the firehose changes.

Revocation

Delegated writes use 60-second single-use tokens: nothing to hunt down. A delegated session is re-checked against the configuration on every request: removal ends it on its next use. Under managing-app, revocation is bounded by the TTL the host chose.

Managing app

A community host holds the roles. The account says "ask did:web:host#community who may write as me". The PDS asks, signed as the account; the host answers with permission strings and an expiry; the PDS caches. The host holds no key and no credential for any community.

The host route: the same design, with no PDS change

callreplywhat the host does

What you keep

No change to the reference PDS, no protocol work, deployable today by whoever runs the host. Existing OAuth clients work. Consent is per account, on the host. Tranquil is already this for its own accounts.

What you give up

The community must live on a group host. Roles, the login method, the narrowing, and the log are the host's own, with no shared representation. In the creation flow the app holds a credential for the community. Migration moves the repo and DID, and leaves the moderators behind unless the next host is the same kind.

Open questions

  • Discovery. Which accounts name me, without every PDS notifying every other.
  • Calling out as the account. An audience-specific rpc: in a delegate entry, if a session ever needs to call one named host as the account.
